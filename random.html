2. Business Logic Implementation Assumptions

This section addresses critical business logic considerations and provides implementation guidance for the enhanced alarm system and event detection mechanisms.

2.1 Multi-Threshold Excursion Event Detection

Normal Temperature Range (20-50°C): This range is designed for standard environmental monitoring applications where room temperature variations need to be tracked. The system uses temperatureUpperLimit1AlarmMark and temperatureLowerLimit1AlarmMark for this range.

Low Temperature Range (2 to 8°C): Specifically designed for pharmaceutical and food supply chain monitoring, this range uses temperatureUpperLimit2AlarmMark and temperatureLowerLimit2AlarmMark.

Question: Should we use temperatureUpperLimit2AlarmMark and temperatureLowerLimit2AlarmMark for excursion detection?

Analysis: Based on the documented temperature ranges and Minew app configuration analysis, the "Limit2" flags correspond to cold chain monitoring (2-8°C range), which aligns with typical pharmaceutical storage requirements.

2.2 Advanced Last Excursion Detection Mechanism

Timestamp Format Considerations

The tempEventTimestamp value uses device-relative timing rather than absolute Unix timestamps. This requires careful handling to convert to meaningful application timestamps.

The enhanced beacon payload provides tempEventTimestamp which indicates the last temperature excursion event time. However, this timestamp is relative to device startup or current time, not an absolute Unix timestamp.

Question: Where does the tempEventTimestamp start from, and should we use this for excursion start time calculation?

Analysis: The tempEventTimestamp appears to be relative to device startup or current operational session rather than Unix epoch time. This is evidenced by the relatively small timestamp values(79616700) that don't align with standard Unix timestamps.
This value is relative time, but it’s unclear whether it starts from the device’s power-on or the excursion event itself. Because of this uncertainty, we still rely on historical data to get the actual date-time of the last excursion event.

Historical Data Continuity If we only use tempEventTimestamp to fetch the last excursion start time, we won’t capture the data point just before the excursion began. As a result, the graph may not show the blue circle or the connecting line leading up to the last excursion.

3. Critical Questions and Implementation Guidance

3.3 Question 3: Historical Data Visualization Continuity

Question: If we use tempEventTimestamp for fetching the last excursion timestamp, how do we maintain graph continuity showing the transition from normal to excursion state?

Analysis: Using only event timestamps creates gaps in data visualization where the transition point (blue circle and connecting line) cannot be displayed without the immediate pre-excursion data point.

Recommended Solution: Implement a hybrid data retrieval strategy:

  • Real-time Monitoring: Use beacon alarm flags for immediate excursion detection
  • Historical Context: Query historical data around event timestamps to retrieve transition points
  • Visualization Enhancement: Combine beacon data with historical queries to create seamless graph transitions
