2. Key Technical Observations

2.1 Payload Structure

{ "timestamp": "2025-07-14 22:04:58", "deviceMac": "C3:00:00:30:18:DB", "temperature": 25.280000686645508, "battery": 100, "firmwareVersion": "3.2.4", "rssi": -101 }

2.2 Critical Issues Identified

⚠️ Payload Size Issue: Historical data payloads are extremely large and cannot be uploaded in a single request. This causes server timeouts and connection failures. (>50k Records)
⚠️ Performance Impact: Connecting and receiving data from beacons takes significant time(>15 secs) due to the large payload size, affecting user experience.
⚠️ Data Persistence: Beacon data persists even after 3-second button press, indicating data clearing mechanism is not functioning as expected.
⚠️ Scanning Interruption: Current implementation stops scanning during device connection, preventing discovery of other devices.

2.3 Data Analysis Requirements

  • Since the payload(Full data stored in beacon) is too large and no flag to indicate the start of any excursion event, we need to parse the full payload to identify any past excursion events.
  • Excursion detection algorithm implemented for temperature range 2-8°C

3.3 System Optimization

Q: Should we implement periodic scanning?
Currently scanning runs indefinitely. Consider periodic scanning to optimize battery and performance.

4. Current Workarounds & Assumptions

4.1 Chunked Data Transfer

Implemented Solution: Sending data in chunks of 1000 records at a time, ordered by most recent first.

  • Prevents server timeouts
  • Ensures complete data upload
  • Maintains data integrity

4.2 Additional Assumptions

  • Excursion events are defined as temperature readings outside 2-8°C range
  • Historical data spans 24 hours by default
  • Device MAC address serves as unique identifier

5. Recommendations
